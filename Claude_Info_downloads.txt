--------------------------------------------------------------------------------
 1. WHY IT EXISTS
--------------------------------------------------------------------------------
Lets people download the tools directly, hosted by Jochen, WITHOUT publishing the
source code. The trick: a PUBLIC repo that contains NO source - only docs and a
small manifest per tool - with the actual installers attached to GitHub *Releases*
(served over GitHub's CDN, free, anonymous download). Source for the open-source
tools stays in each tool's own repository; closed-source freeware ships only its
binary here.

Key mechanic learned: a PRIVATE repo's release assets are NOT anonymously
downloadable (they need an auth token), so public downloads require a public,
code-free repo like this. The alternative (independence from GitHub) is Azure Blob
Storage - same site links, different URL.

This is the PUBLIC channel. It is separate from the site's GATED channel for the
Bizerba tools (jthieren.be /api/download/{tool}, X-CS-Key gated + rate limited) -
never mix them. See [[project-jthieren-site]].

--------------------------------------------------------------------------------
 3. CONVENTIONS
--------------------------------------------------------------------------------
- Tag:            <tool>-vX.Y.Z          e.g. bingocaller-v1.0.1
- Release title:  <Tool> X.Y.Z
- Installer:      <Tool>-X.Y.Z-setup.exe
- Checksums:      SHA256SUMS.txt attached to every release
- Stable URL:     https://github.com/JochenThieren/downloads/releases/download/<tag>/<asset>
- IMPORTANT: /releases/latest is REPO-WIDE (newest release of ANY tool). For a
  tool's true latest, link to tools/<tool>/latest.json - that's why the manifest
  exists.


--------------------------------------------------------------------------------
 4. PUBLISHING A RELEASE
--------------------------------------------------------------------------------
Build happens in the tool's own (often private) repo; only the finished binary is
pushed here. From that repo's CI or by hand:

  gh release create "<tool>-v<version>" dist/<Tool>-<version>-setup.exe SHA256SUMS.txt \
     --repo JochenThieren/downloads --title "<Tool> <version>" --notes-file notes.md

Then this repo's update-manifest.yml regenerates tools/<tool>/latest.json
automatically (triggers on release published/edited; parses the tag into
tool/version; downloads the installer asset to compute sha256 + size; commits).

Cross-repo publishing from a PRIVATE source repo needs a PAT secret in THAT repo
(e.g. GH_PAT) with contents:write on downloads. A release created directly in this
repo needs nothing extra (the bundled github.token covers the manifest workflow).

NOTE (gh not installed here 2026-10-20): the GitHub CLI is not on this machine's
PATH. Releases were driven via the REST API using the cached git credential
(git credential fill -> Bearer token -> api.github.com / uploads.github.com).
GitHub's release JSON uses "key": value WITH a space - parse space-tolerantly.

  TWO LESSONS from the smoke test (important when editing this workflow):
  (a) `on: release` runs the workflow DEFINITION AS IT EXISTS AT THE TAG'S COMMIT,
      not at main HEAD. A fix pushed to main does nothing for a release whose tag
      still points at an older commit - recreate/move the tag onto the fixed commit.
  (b) A release event checks out the TAG (DETACHED HEAD). The commit-back step needs
      actions/checkout with `ref: main` (now set), else `git push` fails with
      "You are not currently on a branch" (exit 128). Also: creating a release fires
      `published` BEFORE assets are uploaded, so the manifest step needs the assets -
      upload them, then PATCH the release to emit `edited` (or attach assets at
      create time).
